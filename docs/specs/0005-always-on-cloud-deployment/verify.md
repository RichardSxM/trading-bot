# 0005. Verify: always on cloud deployment

Run these on the real VPS unless a step says laptop. Steps 1 to 6 belong to milestone 1, 7 to 12 to milestone 2, 13 to 17 to milestone 3, 18 to 20 to milestone 4, and 21 to 22 to milestone 5 (after feature 6).

## One time prerequisites

- OVHcloud panel, optional at first: attach the 50 GB extra disk to the VPS and note its device name (`lsblk`). You can add it later by running bootstrap again with `--data-disk`.
- Tailscale admin console: MagicDNS and HTTPS certificates on; create a one time, tagged auth key for `tag:kfs` (paste `deploy/tailscale-policy.hujson` first, since `tagOwners` must allow the tag).
- GitHub: a classic PAT with only `read:packages`, expiring within a year; store it in the password manager as `ghcr_token`.
- Backblaze: the bucket and the append only key from spec 0003, plus a second key with `deleteFiles` for the drill (password manager only). From the laptop, once: `restic -r b2:<bucket>:kfs init` with the full key.

## Steps

1. **Bootstrap.** From the laptop: `scripts/deploy.sh --bootstrap <public IP> --user ubuntu`, adding `--data-disk /dev/sdX` if the extra disk is attached (OVHcloud's delivered SSH login). Paste the auth key. From the laptop, `tailscale ssh kfs@kfs-vps`, then type `confirmed`. Afterwards, from outside the tailnet (a phone off WiFi): `nc -vz <public IP> 22` fails. On the box: `ss -tulpn` shows only loopback, `tailscale0`, and UDP 41641. Then `swapon --show` (2G), `sysctl vm.swappiness` (10), `chronyc tracking` (synchronised), `timedatectl` (UTC), `docker info | grep -i live` (true), `findmnt /srv/kfs` (by UUID, `nofail`; only once the extra disk is added), `apt-config dump | grep -A2 -E 'Allowed-Origins|Automatic-Reboot '` (only the security origin, reboot false), `sudo -l -U kfs` (only `/usr/local/sbin/kfs-*`, no password), `grep VERSION_ID /etc/os-release` (26.04). Run it again: every line `ok`, nothing `changed`. Record the Kraken connect baseline it prints in this file. Later, with the extra disk attached: `sudo /opt/kfs/current/deploy/host/bootstrap.sh --data-disk /dev/sdX` moves the catalog onto it, then `findmnt /srv/kfs` and `ls -a /srv/kfs/catalog` (`.kfs-volume` present). Proves **AC-1**.
2. **Secrets.** `sudo /opt/kfs/current/deploy/host/place-secrets.sh`: it asks only for missing files, no echo, logs in to GHCR, then runs the dashboard credentials from the pulled image (set a password, scan the QR). After it, `ls /etc/kfs/secrets` lists every file the Compose files name. Paste a value with a space: refused. Run it again: nothing asked. `--rotate redis_dashboard_password`: only that one replaced, its new fingerprint printed. `ls -ln /etc/kfs/secrets`: 10001, 0400 (`ghcr_token` root). `docker login ghcr.io` already done; `ps` during the run shows no secret. Proves **AC-2**.
3. **Images.** Push a commit to a branch: no image job. Merge to main: the `images` job pushes four images (five after milestone 4) tagged with the commit, and `docker inspect` shows `GIT_COMMIT` equal to it. After 11 main pushes, each package has 10 versions. Proves **AC-3**.
4. **First deploy.** From the laptop: `scripts/deploy.sh`. Every service healthy within 180 s, `https://kfs-vps.<tailnet>.ts.net` shows the login, and the heartbeat's `git_commit` matches. `tail -1 /var/log/kfs/deploys.jsonl` has every field. Try `scripts/deploy.sh <a branch commit>`: refused. Run two deploys at once: the second exits 3. Fill `/` to under 5 GB free (`fallocate`): exit 4, then remove the file. Proves **AC-4**, **AC-12**.
5. **Compose wrapper.** Deploy twice, then `docker volume ls`: one `kfs_pgdata`, one `kfs_redisdata`, and the rows from before are still in Postgres. `kfs-compose config | grep -c kraken_api` is 0 with `TRADING_ENV=demo`. On the laptop, `docker compose config` still uses the old project name and `kfs/<app>` images. Proves **AC-5**.
6. **Tailnet and the 0004 carryover.** From another tailnet identity (a shared device or a test user): 443 and SSH to `kfs-vps` fail. From the VPS, `tailscale ping <your laptop>` and `nc -vz <laptop tailnet IP> 22` fail. Then spec 0004 verify steps 1, 6, and 12 on the VPS: the three login files exist from step 2 (owner 10001, mode 0400), log in with the QR you scanned there, check the shell at phone size over Tailscale, and in airplane mode tap stop: `Stop NOT sent`. Proves **AC-22**, **AC-23**.
7. **Pause and unpause.** On the System page tap Pause: `pause sent · awaiting trader`, then `confirmed` within 2 s, and the top bar reads `paused · by you`. Heartbeat `trading_state` is `REDUCING`. In Postgres, `control_commands` has the row. Tap Resume: `ACTIVE`, the top bar clears. Append the same `id` again as `trader` in redis-cli: `duplicate`. Append an expired pause: `expired`, still `ACTIVE`. Tap stop: `failed`, reason `not_implemented`. Proves **AC-6**, **AC-13**.
8. **Pause survives restart.** Pause, then `kfs-compose restart trader`: it comes back `REDUCING` and `paused · by you`. Resume. Proves **AC-6**, **AC-14**.
9. **Trader state snapshot.** `sudo kfs-compose run --rm --no-deps -T dashboard python -m dashboard.control_cli state` prints every AC-7 field, and `ts_ns` advances every second. Stop Redis for 10 s: `state` exits 1. Proves **AC-7**.
10. **Drain, abort, and resume rules.** Pause from the dashboard, then deploy a commit with a new trader image: the deploy sends no pause, does not unpause, and the top bar still reads `paused · by you`. Resume. Make the trader look not flat (a demo entry order far from the market once feature 6 exists; before then, a unit test with a fake snapshot) and deploy with `--wait 1m`: `aborted_not_flat`, exit 2, nothing switched, the trader resumed. `--now`: pauses, deploys, resumes. Stop the dashboard and deploy: abort, exit 2. Proves **AC-8**, **AC-11**.
11. **Rollback.** Deploy a main commit whose trader exits at boot (a deliberate `raise` behind a flag set in `kfs.env`, removed afterwards): `rolled_back`, exit 1, the previous release healthy, `alembic current` unchanged by the rollback. `ls /opt/kfs/releases` shows current plus at most two. Proves **AC-10**, **AC-12**.
12. **Graceful shutdown.** With a demo entry order resting and a position with its stop (after feature 6; before then, a trader test with a fake strategy): `kfs-compose stop trader`. The log shows `shutdown_graceful` with 1 cancelled, 1 kept, 1 stop kept, and exit code 0 within 30 s. Proves **AC-9**.
13. **Kill.** `docker kill` each of postgres, redis, trader, recorder, dashboard, backup in turn: each is back healthy within 2 minutes, and the data is still there. Proves **AC-14**.
14. **Hang.** `sudo kill -STOP $(sudo docker inspect -f '{{.State.Pid}}' kfs-trader-1)` (from the host; the kernel ignores it from inside the container): unhealthy after about 30 s, `journalctl -u kfs-autoheal` shows `autoheal_restart`, healthy again. Repeat three more times within the hour: the fourth logs `autoheal_gave_up` and the container stays unhealthy. `docker restart` it by hand and delete its entry from `/var/lib/kfs/autoheal.json`. Proves **AC-15**.
15. **Docker restart.** Note the trader PID (`docker inspect -f '{{.State.Pid}}'`), run `systemctl restart docker`: the same PID, every service healthy. Proves **AC-16**.
16. **Reboot.** `sudo reboot`: within 5 minutes every service is healthy and the dashboard answers. Then `sudo kfs-safe-reboot`: it pauses, reboots, and after boot `kfs-post-boot` resumes; the top bar is clear. Pause by hand first, then `kfs-safe-reboot`: after boot it stays `paused · by you`. Proves **AC-17**.
17. **Missing disk.** Comment out the `/srv/kfs` fstab line and reboot: the recorder logs `catalog_volume_missing` and stays down, everything else is healthy. Restore the line and reboot. Proves **AC-18**.
18. **Append only key.** On the VPS, with the backup container's key: `restic forget --keep-last 1` fails with a permission error, and `restic backup` of a test file succeeds without a stale lock warning on the next run (the milestone 4 gate). Proves **AC-20**.
19. **Nightly backup.** Set `BACKUP_AT_UTC` to two minutes ahead and redeploy (or restart backup): `backup done` with a snapshot id and the manifest. `restic snapshots` from the laptop shows the tags. `restic ls latest | grep -c secrets` is 0. Break the B2 key file: `backup_failed` with `step: upload`. Age `/staging/last_success` past 26 h (`touch -d`): the backup turns unhealthy. Proves **AC-19**.
20. **Restore drill.** On the laptop: `scripts/restore-drill.sh`, paste the restic password and the delete capable key: `PASS`, the container is gone, `restic snapshots` afterwards follows 14/8/24. Run it with `--self-test`: `FAIL` naming `fills`. Proves **AC-21**, **AC-20**.
21. **Deploy during a position** (after feature 6). With an open demo position and its stop: `scripts/deploy.sh`. It pauses, waits until the strategy exits, deploys, resumes, and `waited_for_flat_s` is in the deploy line. No order lost its stop at any sample. Proves **AC-8**, **AC-9**.
22. **Soak** (after feature 6). `sudo kfs-soak start`. Touch nothing for 72 h (the nightly backups run). `sudo kfs-soak report`: all healthy, longest gap under 2 minutes, restarts listed, fill counts equal, stops covered at every sample. Watch `docker stats` once a day and note the peaks here. Proves **AC-24**.
