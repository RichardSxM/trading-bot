# 0011. Verify: leverage and liquidation guard

The end to end check of AC-20 on the VPS demo, after the deploy. Unit, engine level, and integration tests cover the rest (see the spec's Critical test scenarios). Record each result here with its date (UTC).

Commands run on the VPS as `kfs`. `psql` below means `sudo -n kfs-compose exec -T postgres psql -U trading -d trading -c`.

1. **Deploy (AC-19).** Run `scripts/deploy.sh` from the laptop. The health gate passes, and the trader starts with the six `RISK_*` settings (no `config_invalid` in its log). Result (2026-10-15, VPS, release 8dfc86e): **pass on the second try**. The first deploy (07:56 UTC) rolled back: `/etc/kfs/kfs.env` lacked `RISK_TOTAL_LOSS_SINCE`, which this release is the first to need (spec 0010, no default on purpose), so the trader refused to start and the gate failed. After adding `RISK_TOTAL_LOSS_SINCE=2026-10-15`, the 08:04 deploy waited 7 s for flat, and the gate passed after 66 s. All seven services were healthy, there was no `config_invalid`, and `loss_seeded` read `realized_total -2.30` from 2026-10-15.
2. **Sized entries (AC-1, AC-2, AC-12, AC-20).** After the next placeholder boundary, read the newest entry decision: `psql "SELECT decided_at, intent, risk_verdict, risk_reason, inputs FROM decisions ORDER BY decided_at DESC LIMIT 3"`.
   - `inputs` holds every AC-12 figure: `equity`, `entry_px`, `stop_px`, `open_notional`, `taker_fee`, `maintenance_rate`, `funding_rate`, `funding_periods`, `loss_per_unit`, `risk_quantity`, `quantity`, `limited_by`, `liq_px`, `liq_distance_pct`.
   - For an approved entry, the order's quantity in `orders` equals `inputs.quantity`, and `quantity` is at most `risk_quantity`.
   - `funding_periods` matches the top of the hour boundaries inside `decided_at` plus `PLACEHOLDER_HOLD_MIN` (0 when the hold ends before the hour), and when it is above 0, `funding_rate` is not null.
   Result (2026-10-15, VPS, 8dfc86e): **fail: fees missing from the sizing**. The 08:15:02 entry was approved and `inputs` held every AC-12 figure. `quantity` 0.0030 is at most `risk_quantity` 0.0175, with `limited_by` `notional_cap` (0.003 × 81 241.5 = 243.7 ≤ 250). Both orders (market buy, stop sell) carry 0.003. `funding_periods` was 0, which is right: the hold ended at 08:25, before the hour. But `taker_fee` was `0`, so `loss_per_unit` 284.9985 is only the stop distance (244.5) plus 5 bps slippage (40.4985). Each fill was charged 0.12 USD (0.0005 × 243.7). The placeholder reads `instrument.taker_fee` from the trader's cache, which holds the adapter's instrument with fee 0. `FeeSandboxExecutionClient` applies `SANDBOX_TAKER_FEE` only to its own simulated exchange (`node/sandbox.py`). The loss per unit is about 28 % too low (the round trip fees, about 81 USD per unit, are left out). Here the notional cap bound first, so nothing was oversized. Owed to `/debug`: where the guard's fee should come from, in demo and in live.
   Rerun (2026-10-15, VPS, cd7c0f8, after the fix in PR #41, `GuardedConfig.taker_fee`): **pass**. The 09:45:02 entry (a short) was approved with `taker_fee` `0.0005`. `loss_per_unit` 366.49575 is the stop distance (81 412 − 81 167.5 = 244.5), plus 5 bps slippage on the stop (40.706), plus 0.0005 × (81 167.5 + 81 412) = 81.28975 in fees. `quantity` 0.0030 is at most `risk_quantity` 0.0136, with `limited_by` `notional_cap`. Both orders (market sell, filled at 81 167, and stop buy, accepted) carry 0.003. `funding_periods` was 0 (the hold ends at 09:55), with `funding_rate` set.
3. **Liquidation on every snapshot (AC-8, AC-20).** While a position is open: `psql "SELECT captured_at, quantity, mark_px, liquidation_px FROM position_snapshots ORDER BY captured_at DESC LIMIT 5"`. Every row has a `liquidation_px`, null only at 1x or below (no liquidation). No `liq_near:` risk event exists. Result (2026-10-15, VPS, 8dfc86e): **pass, at under 1x only**. Both snapshots of the 08:15 position (08:15:02 and 08:15:38) carry `liquidation_px` null. That is right at 0.24x leverage (243.7 USD against 1 000 equity). The decision's `liq_px` and `liq_distance_pct` are null to match, and there are no `liq_near` events. With the 250 USD order cap against 1 000 equity, the demo placeholder never reaches 1x. The non null path rests on the unit and engine tests.
   Later (2026-10-15, VPS, cd7c0f8): the non null path showed up on a short. The 09:45 short of 0.003 has a `liquidation_px` on every snapshot (about 410 357, for example 09:47:03, 09:48:03, 09:49:03), and the decision's `liq_px` 410 356.68 matches. That is right: a short can be liquidated at any leverage, so "null only at 1x or below" holds only for longs. There are still no `liq_near` events.
4. **Funding booking (AC-13, AC-14).** The placeholder never holds across the hour, so nothing is expected in `funding_payments` and `funding_unbooked` events are not expected either. Proof is the engine level test of AC-13. Check only that no position has a non zero `funding_total`. Result (2026-10-15, VPS, 8dfc86e): **pass**. `funding_payments` holds 0 rows, and no position has a non zero `funding_total`.
   Later (2026-10-15, VPS, 8dfc86e and cd7c0f8): **bug found**. At every top of the hour (09:00, 10:00:00) the trader logged `recording_failed`: `RecordingActor._arm_funding` set the `recording_funding` alert again from inside its own callback, and the live clock still holds a firing alert's name, so `set_time_alert_ns` raised `KeyError`. That blocked entries until a restart (the 09:15 and 09:30 entries were refused with `blocked:recording_failed`), and the next funding alert was never set. Fixed by cancelling before setting, as the placeholder already does (PR #42). Recheck after its deploy: no `recording_failed` at the next top of the hour.
   Recheck (2026-10-15, VPS, 96df3cb, deployed 10:38): **pass**. There was no `recording_failed` and no error at 11:00 or 12:00. Two boundaries in a row show that the alert is set again after it fires. The entries at 11:15 and 11:45 were approved. The refusals at 11:00, 11:30 and 12:00 were `blocked:loss_cooldown` (spec 0010), not this bug. `funding_payments` still holds 0 rows.
