# 0009. Verify: market context feed

The checks that need real Kraken data or the VPS. Unit and integration tests cover the rest (see the spec's Critical test scenarios). Record each result here with its date (UTC).

## Gate results (Milestone 0)

1. **Native streams.** Cadence of mark, index, and funding updates on `PF_XBTUSD`; the price precision of mark and index; whether non fill trades also arrive as `TradeTick`; whether `FundingRateUpdate.rate` is relative or absolute; the funding period. Result (2026-10-11 22:45 to 23:00 UTC, laptop, one off container on the recorder image, no keys): **pass**. Mark, index, and funding each arrive with every Kraken ticker push, all three on the same `ts_init`: about 1.76 per second each, median gap 0.38 s, longest 2.2 s. The max age defaults (30 s, 7 200 s for funding) are well above 3 times that, so none is raised. Mark and index come at precision 0 (whole dollars: `83597` while REST said 83597.75), the instrument's tick; recorded as given, so basis resolves to about 1.2e-5. `FundingRateUpdate.rate` is the **relative** rate (`0.000014034466666667`, equal to REST `relativeFundingRate`; the absolute `fundingRate` was 1.17), so AC-14 stands. Period one hour: at 23:00:01 the rate changed and `next_funding_ns` moved on by 3 600 s. Every `TradeTick` seen was a fill; with no liquidation in the window, whether non fill trades also arrive as `TradeTick` stays open, so no `trade_tick` join is claimed (Data model).
2. **Raw feeds.** `openInterest` present on `ticker`; the `type` values seen on `trade`; `side` is the aggressor; `trade_snapshot` on subscribe. Fixtures saved under the core tests. Result (2026-10-11 22:45 to 23:12 UTC, `websockets` 15.0.1): **pass, liquidations unseen**. `ticker` carries `openInterest` on every push (about 1.86 per second, up to 4 decimals, the size precision). `trade_snapshot` came once right after subscribing, with 100 rows. All 1 516 trades were `fill`: no liquidation in 26 quiet minutes (Kraken's REST history showed only fills too). Kraken's docs (futures websocket `trade`) still list `type` as `fill`, `liquidation`, `termination`, `block`, and `side` as "the taker side", so liquidations stay in. Fixtures: `packages/core/tests/fixtures/kraken_context/feed_2026-10-11.jsonl` (real messages, the snapshot cut to 3 rows); liquidation rows in tests are built from the documented shape and say so.
3. **Custom types.** Streamed to feather, read by `read_chunks`, written by `HourSink`, read back by `ParquetDataCatalog` and the `BacktestEngine` with exact Decimals; the two table names. Result (2026-10-11): **pass**. Two `Data` subclasses registered with `register_arrow` (values as strings, `@customdataclass` cannot hold `Price`, `Quantity`, or `Decimal`) streamed through `StreamingConfig` into per instrument folders, `read_chunks` read them, `HourSink` wrote them, and `ParquetDataCatalog` plus a `BacktestEngine` actor read all rows back with exact values. Table names: `custom_open_interest_update` and `custom_liquidation_tick`. Gotchas for the build: the writer reads the schema list when it is built, so the types must be registered at import; the catalog returns `CustomData` with empty metadata, so the lab rewraps each row as `DataType(cls, metadata={"instrument_id": id})`; `subscribe_data` needs `instrument_id=`; `BacktestEngine.add_data` needs a `client_id` for custom data.
4. **Size estimate.** Rows and bytes per day per stream. Result (2026-10-11, the captures above written as the compactor writes them): `mark_price_update` 152k rows and 1.8 MB a day, `index_price_update` 152k and 1.8 MB, `funding_rate_update` 152k and 1.8 MB, `custom_open_interest_update` 161k and 2.2 MB; liquidations a few rows. About 7.5 MB a day in all, small next to the book.
